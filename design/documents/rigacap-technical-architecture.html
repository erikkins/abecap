01 · System Overview

A serverless platform with a scheduled heartbeat.

RigaCap is a serverless, event-driven signal platform on AWS. It ingests daily market data for roughly four thousand US equities through a dual-source pipeline, ranks that universe through a regime-adaptive momentum engine, and delivers the result as two subscriber tiers — Preserver and Maximizer — through a React dashboard, an automated email pipeline, a weekly newsletter, and a moderated social engine.

The backend runs on two specialized AWS Lambda functions — an API Lambda for HTTP traffic and a Worker Lambda for scheduled and long-running jobs — both built from a single container image and differentiated by an environment variable. FastAPI sits on top of Mangum for ASGI compatibility. PostgreSQL 15 on RDS is the system of record. S3 holds the historical price cache and the pre-computed dashboard JSON that CloudFront serves to subscribers; an ElastiCache Redis node fronts hot read paths.

Two-Lambda split. The API Lambda is small and fast (1 GB, 30s timeout) because subscribers expect dashboard loads under two seconds — it never loads the price store and reads only S3 JSON and the database. The Worker Lambda is large and patient (4 GB, 900s timeout) because daily scans, walk-forward simulations, and email runs need both memory and time. One image, two roles, atomic deploys.

Request and event flow

# Subscriber request path React 18 SPA → CloudFront → WAF → API Gateway → API Lambda → RDS / Redis / S3 (read) # Scheduled / event-driven path EventBridge → Worker Lambda → RDS / S3 (read+write) → Step Functions (walk-forward fan-out) → Claude API (content, autopsies, optimization) → SES (email) → X / Threads / Instagram (social)

What the platform produces

  • Two tiers of daily signal. A single scan produces both the Preserver (protect) and Maximizer (grow) reads, cached as JSON on S3 and fronted by CloudFront for sub-second dashboard loads.
  • Daily digest email. Per-subscriber summary of signals, watchlist, regime context, and any sell alerts — gated on a same-day data-freshness check.
  • Weekly newsletter. A market-commentary issue, locked as a draft on Saturday and published Sunday morning.
  • Social posts. AI-drafted from real walk-forward and live results, gated by one-click admin approval, auto-published Monday / Wednesday / Friday across X, Threads, and Instagram.
  • Mobile push notifications. Sell alerts and high-conviction signal events through Expo.

Signals only. RigaCap publishes signals; subscribers execute at their own broker. The platform never touches customer funds and holds no brokerage integration — a deliberate architectural boundary that keeps the system a publisher, not a manager (see §12 disclosures).

05 · Data Pipeline & Caching

Two sources, one truth.

The platform ingests daily market data from two providers with automatic failover, adjusts it once at read time, and exposes a single read interface everywhere downstream — so the production scanner and the walk-forward simulator see exactly the same bars, to the penny.

Dual-source ingestion

A DualSourceProvider wraps Alpaca and yfinance with health tracking and auto-failover. The split arose from a stale-data incident: relying on a single vendor left a two-day gap that reached subscribers. The provider now routes each use case to the source that is most reliable for it, and falls back automatically when a source degrades.

Use casePrimaryFallbackReason
Daily EOD barsAlpacayfinanceFaster and more reliable for bulk historical pulls.
Live intraday quotesyfinanceAlpacaAlpaca free tier is IEX-only; yfinance covers all exchanges.
Index data (^VIX, ^GSPC)yfinance—Alpaca does not serve index symbols.
Sector ETFsAlpacayfinanceNormal tickers, Alpaca-compatible.

If more than ten percent of symbols fail during a daily scan, the pipeline automatically retries the failed set against the yfinance fallback. Symbol normalization reconciles the hyphen/dot mismatch between providers (BRK-B ↔ BRK.B). Splits are pulled on every ingest so the cached history stays split-adjusted, preventing the unadjusted-split artifacts that surface after large stock splits.

Storage layers

Per-symbol price store
S3 · adjust-at-read
Raw daily bars persisted per symbol and split-adjusted at read time, so the same canonical history drives both the live scanner and the walk-forward simulator. Refreshed daily; a weekly full rebuild incorporates new universe symbols.
Parquet columnar store
prices/all_data.parquet
Columnar, compressed, schema-enforced via pyarrow. Enables partial reads (one symbol without loading the full blob) and DuckDB SQL — the change that took the Worker's scan footprint from OOM-risk down to comfortably inside its ceiling.
CDN dashboard JSON
dashboard/latest.json
Pre-computed at scan time and fronted by CloudFront with a one-hour TTL. The dashboard, the daily digest, the sell-alert dispatcher, and the intraday monitor all read from this single JSON so emails and the UI never disagree on the day's signals.
Data-integrity filters
scanner data-quality gate
Rejects extreme price ratios, single-day moves above a log-return threshold, and multi-day gaps — the ticker-reuse signature. Catches unadjusted splits, stitched histories, and delisting artifacts in real time.

Freshness gate

Every subscriber-facing communication job (daily digest, sell alerts, double-signal alerts) validates that the daily scan ran successfully today before it sends. If the data is stale, emails are held and the operator is alerted rather than shipping a subscriber a signal computed on yesterday's prices. The dashboard exposes the same state publicly through /api/market-data-status, which drives a staleness banner in the UI.

Layer-2 data hygiene

Each weekday evening the nightly_data_hygiene rule runs a protection pass against silent data drift:

  1. Asset-ID verification. Compares each symbol's stored Alpaca asset UUID to the current value; any change is treated as ticker reuse — auto-quarantine plus admin alert.
  2. Corp-actions poll. Queries the Alpaca corporate-actions API for splits, dividends, spin-offs, mergers, and delistings.
  3. Split auto-refetch. For each detected split, fetches a clean split-adjusted history and overwrites the cache.
  4. Store re-export. The updated cache is re-exported so the read stores never diverge.
  5. Post-actions diagnose. A DuckDB scan over the fresh parquet flags anomalies above threshold.
  6. Admin digest. Auto-remediated items report as INFO; only true anomalies escalate.
06 · Backend Services & Tier Serving

One scan, two reads.

The backend is a set of singleton service classes instantiated at module load and imported across handlers. Mangum translates ASGI calls into Lambda invocations on the API path; the Worker Lambda dispatches EventBridge payloads through a handler map.

How the two tiers are served

RigaCap is a two-tier product — Preserver (protect capital) and Maximizer (grow / breakout). Both are produced by the same regime-adaptive momentum engine over the same universe on the same daily scan; they differ in their exposure and risk posture, not in a separate data path. A single scan computes both reads and writes both into the dashboard JSON, tagged by tier. At request time, the subscription tier on a user's account gates which read they see: Preserver is the base, and Maximizer is a paid add-on unlocked through Stripe. This keeps a subscriber's live experience faithful to the tier they pay for, and keeps both tiers reconciled to the same underlying walk-forward record.

Marketing-parity discipline. The engine warm-starts from full history on every run — production has years of bars, and starting cold would misprice the risk controls. Any figure a subscriber sees, and any exit parameter stated in the UI or an email, must be the live tier value, so the published record is actually realizable by a subscriber who mirrors it.

Risk machinery (public-safe description)

Seven-regime market classifier
strong_bull / weak_bull / rotating_bull / range_bound / weak_bear / panic_crash / recovery
Daily classification from a broad-market indicator stack (long-term trend, breadth, volatility). The classified regime modulates exposure, sizing, and exit thresholds — the mechanism behind “momentum, built around the drawdown.” Snapshots persist for heatmap visualization and accuracy tracking.
Cascade Guard (circuit breaker)
state persisted to S3 per portfolio type
When many positions hit their trailing stops on the same day — the cascading-stress signature — the guard pauses new entries for a cooling window. State persists to S3 so the breaker survives Lambda cold starts. Externally this is “Cascade Guard”; internally it is the circuit breaker.

09 · Social & Content Engine

Real trades in, moderated posts out.

The social engine turns real walk-forward and live results into editorial posts — drafted by Claude, approved by a human in one click, and published on a fixed cadence across three platforms. Nothing reaches an audience without an operator's explicit approval.

The pipeline

  1. Draft. The nightly walk-forward and live-trade events feed AIContentService, which prompts the Claude API to write posts grounded in the actual result — result-and-thesis first, methodology hygiene left out of customer copy. A template service is the fallback if the API is unavailable.
  2. Schedule. PostSchedulerService spreads approved drafts across optimal posting windows on a Monday / Wednesday / Friday autopost cadence, capped per day, and issues T-24h and T-1h admin notifications.
  3. Approve or Kill. Each notification email carries a JWT-signed one-click Kill or approve link, and an edit path back into the queue — no login required, scoped to a single post ID.
  4. Publish. A cron every fifteen minutes publishes any approved post whose scheduled_for has passed.

Contextual replies (deep-link workaround)

A reply scanner surfaces on-thesis conversations across X and Threads and drafts a contextual reply for approval. Because the X free tier cannot programmatically post replies where the account was not mentioned, the approval email deep-links to the platform's pre-filled composer (an in_reply_to intent URL) rather than posting through the API. The operator taps once and sends. First-party posts still publish through the API directly — only replies use the deep-link path.

Human in the loop, by design. Every AI draft — post or reply — is gated behind explicit approval. The Kill link makes the default action “do nothing” safe: an unapproved post simply never ships.

10 · Security Architecture

Defense in depth, not in marketing.

Every signal endpoint sits behind a subscription guard. Every admin endpoint sits behind two. The price-data S3 bucket has all public access blocked. The raw execute-api URL is not reachable directly. None of this is novel; all of it is enforced and re-verified on a fixed cadence.

11 · CI/CD, DR & Deploy Safety

Push to main, the rest is plumbing.

Every change ships through GitHub Actions on push to main. The pipeline tests, builds the frontend, builds the Lambda container image, deploys to ECR, updates both Lambdas to the same image, and warms the API. Manual deploys are reserved for CI outages.

# Trigger: push to main (deploy) OR PR to main (test only) Stage 1: Test Backend → Python 3.11 → pip install → pytest -v Frontend → Node 18 → npm ci → npm run lint && npm test Stage 2: Deploy (only on main push) 1. npm run build → S3 sync → CloudFront invalidation 2. docker buildx --platform linux/amd64 --provenance=false --sbom=false 3. ECR push → Lambda update-function-code on API + Worker 4. Post-deploy: GET /api/warmup (verify cold start healthy)

Lambda build requirement. Docker BuildKit creates multi-platform manifests with attestations that Lambda rejects. All builds use --provenance=false --sbom=false to produce the single-platform linux/amd64 image Lambda requires.

The environment-clobber landmine, disarmed

Two operational footguns have bitten this platform and are now guarded against in the tooling itself:

  • Never update-function-configuration --environment. That flag replaces the entire environment block, which would wipe the database URL, Stripe keys, and JWT secret in one call. Cold starts are forced with update-function-code against the current image instead.
  • Terraform cannot clobber live env either. Both Lambdas carry lifecycle { ignore_changes = [image_uri, environment] }. The live functions accumulate keys through the container deploy path; without the guard, a blind apply would drop keys and revert values — a full outage. Plans still get reviewed before apply.

Migration discipline

SQLAlchemy auto-includes every model column in SELECT queries, so a column that exists in the model but not yet in the database breaks every query against that table — including auth. The platform follows a migration-first pattern: deploy the migration SQL first via the run_migration Lambda event, verify the columns exist, then deploy the model change in a second commit. Schema changes never ship during business hours.
